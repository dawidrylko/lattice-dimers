Each directory holds the entry text, where there is one the b-file and the PARI/GP program, and a README with the contribution and its status. The OEIS is the authoritative copy, and its editors may still change a proposed draft before they approve it.

## Files

The entry texts `A*.txt` are in the OEIS internal format. Published lines come from `https://oeis.org/search?q=id:<A-number>&fmt=text`, without the keywords `new` and `changed` that the OEIS sets for a while on its own; a proposed draft exists only as the HTML of its draft page, and its text is reconstructed from that page. A new entry is given in full, with the data on one `%S` line; an existing entry holds only the lines this repository contributed.

Each b-file `b*.txt` is printed by its [generators](../docs/glossary.md) next to it. `b<number>.rs`, `b<number>.py` and `b<number>.js` run the same method in Rust, Python and JavaScript, each in its own code, so a mistake in one of them shows as a difference from the b-file. `node oeis/buildBFiles.js` rebuilds the b-files with the JavaScript generators, all of them or the entries it is given, such as `node oeis/buildBFiles.js A402163`. With no entry given it runs every JavaScript generator over its whole b-file, which by the full runs of 17 November 2026 takes about two hours on an Apple M4, an hour of it for A401988, whose JavaScript generator runs on one core. `node oeis/buildBFiles.js --check` compares each b-file with exact counts committed elsewhere in this repository, from [`spec/cases/`](../spec/cases/) and [`research/king-entropy/data/zex`](../research/king-entropy/data/zex), or for A004003 with [`domino-rectangle-formula.js`](../js/solvers/domino-rectangle-formula.js), up to the terms they hold. The README of each entry names the generators and these checks in its row of the b-file.

The programs `A*.gp` hold the PARI/GP programs of the entry texts, laid out over several lines; `A401670.gp` and `A402163.gp` also define `T(h, w)`, for the $h \times w$ torus and the $h \times w$ cylinder.

`cargo test --release` in `rust/`, `python -m pytest python/tests` and `pnpm -C js test:oeis` run each generator from $n = 0$ up to its last term in [`spec/limits.json`](../spec/limits.json) and compare the output with the b-file. The last terms are set so that one run takes about 30 s in CI, except that the Rust generator of A401988 runs its whole b-file, in about 50 s. `FULL_CASES=1` runs every term. `GENERATOR_CHECKS=skip` skips those runs. CI sets it for a pull request that changes nothing the generators depend on, which the step "Select the generator checks" of [`ci.yml`](../.github/workflows/ci.yml) lists: the b-files and their generators, the code the generators import, their tests, `spec/limits.json`, the toolchain files and the workflow. The step fails rather than skip when it cannot tell what changed.

## Editor rules

[`editorRules.js`](editorRules.js) turns what the OEIS editors corrected in these entries, and what the [OEIS Style Sheet](https://oeis.org/wiki/Style_Sheet) asks for, into checks on an entry text, one rule per correction with the revision that made it. `node oeis/editorRules.js --rules` lists them with their sources.

A finding is a defect: an editor already corrected that kind of line, or the Style Sheet requires it. Advice is shown and never fails a run. Three rules only advise: `links-mathworld`, since A401669, A401670 and A401673 were approved without the MathWorld links that an editor added to other entries, `program-shared`, one program kept in one entry, and `links-arxiv-version`. That one asks for a line for the arXiv version beside a DOI link, as Vaclav Kotesovec added to A401988 in #13, since offline the script cannot see whether the article is open access. Two more advise in part. `data-rows` advises a further whole row of a triangle, while a row cut short stays a defect, and `crossrefs-reverse` advises a reply in an entry with no copy here, such as a general sequence like A000012. A note says what the script could not check. `data-fill` counts DATA with the spaces the OEIS shows, up to 290 characters: Michel Marcus left A402163 at 287 (#5), past the 260 of the Style Sheet that Alois P. Heinz wrote on A309117 (#8).

`comment-provenance` and `comment-future-proof` match the wording editors removed, so a reworded sentence of the same kind passes them. A run without findings does not replace reading COMMENTS.

`node oeis/editorRules.js` checks the entry texts here and ends with a count of defects, advice, notes and accepted findings. `node oeis/editorRules.js A401670` checks one of them, and an entry that is not here is an error. Some findings stay on purpose: the entry on the OEIS still has the line, or the copy of a draft waits to be synced after approval. `ACCEPTED` keeps each of them with a fragment of the line it covers and its reason. Another line of that entry under the same rule is a defect, and the test fails once an accepted finding no longer fires, so the list shrinks with the copies.

`node oeis/editorRules.js --draft <A-number> <draft page .html>` checks a draft before it is submitted. It rebuilds the text from the block of edits on the saved draft page, and `-` reads the page from standard input. With no file the script fetches the page and gives up after 30 seconds; where that fails, save the page with `curl` and pass the file. `--print` writes that text to standard output without the keywords the OEIS sets by itself (`new`, `changed`, `allocated`, `recycled`) and sends the findings to standard error. The text has no `%I` line, which names the revision: a copy in `oeis/` takes it from the approved entry, saved with `fmt=text`.

`node oeis/editorRules.js --file <entry .txt> [b-file]` checks a text in the internal format before it goes into the form. Both modes take the b-file in `oeis/` when no other is given and say so when there is none, since `data-fill` and `data-rows` then see only DATA. Both compare with the copy in `oeis/`, if there is one, for the credit of the b-file line. `--related <file>` passes the text of an entry that a CROSSREFS sentence names, saved from `https://oeis.org/search?q=id:<A-number>&fmt=text`, so that `crossrefs-reverse` can check that it names the draft back. An entry with only a partial copy here and no `--related` gets a note, and the check of the copies in `oeis/` says nothing about it. `ACCEPTED` does not apply to a draft. The exit code is 1 on a defect, 2 when an input cannot be read or the arguments are wrong, and 0 otherwise.
